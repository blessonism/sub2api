# brainstorm: 管理员校准用户 Token 用量和余额

## Goal

提供一个仅管理员可用的校准能力，用于在发现用户 Token 使用量或余额存在偏差时进行人工修正；修正结果应影响系统内部账务/统计口径，但不应作为普通用户可见的使用记录暴露给用户。

## What I already know

- 用户希望新增功能，而不是只做一次性脚本处理。
- 功能对象是“用户使用 token 量”和“余额”。
- 校准记录不需要让用户看到。
- Token 用量校准需要影响统计口径；如果不影响，用户侧汇总和后台校准结果会对不上。
- 余额校准不允许把用户余额扣成负数。
- Token 用量校准允许管理员指定统计归属时间，默认今天，也可以选择历史日期。
- 管理员希望有一个入口可以查看某个用户的使用记录，展示效果要和该用户自己看到的一样。
- 入口位置应在用户版使用记录页的筛选行：在 API 密钥下拉栏左侧增加选择用户入口，并在同一行新增校准入口。
- 选择用户入口和校准入口只对管理员可见，普通用户不能从页面、接口或记录中察觉这些后台能力。
- 校准表单需要同时支持“增减量”和“设置为目标值”两种模式。
- Token 目标值模式需要管理员在校准表单中单独选择计算范围，而不是隐式复用页面当前筛选范围。
- Token 校准差额需要按计算范围内每天的原始 Token 占比分摊到各天。
- 如果 Token 目标值模式的计算范围内原始 Token 总量为 0，应拒绝目标值校准并提示无法按比例分摊。
- 当前仓库是 `Wei-Shaw/sub2api` 的下游二开仓库，任务实现需遵守下游 fork 分支边界。

## Assumptions (temporary)

- 该能力面向管理员后台，而不是用户自助入口。
- 校准应支持正向和负向调整，避免只能补扣或只能补偿。
- 普通用户不可见不等于系统完全不留痕；为了审计和排错，管理员侧仍应能看到校准记录。
- 校准应避免伪造一条普通消费记录，否则会污染用户明细、排行榜或日/周统计。

## Requirements (evolving)

- 管理员可以对指定用户执行 Token 用量校准。
- 管理员可以对指定用户执行余额校准。
- 校准操作不出现在普通用户可见的使用记录中。
- 校准操作需要保留管理员可查的内部痕迹，用于追溯谁在何时因为什么原因调整了什么。
- 校准记录不应复用会进入普通用户兑换历史的现有 `redeem_codes` 用户历史口径。
- Token 用量校准需要影响用量汇总、排行榜和运营统计等聚合口径，确保用户侧可见的总量和后台校准后的结果一致。
- Token 用量校准不应伪装为普通模型请求，否则会污染用户请求明细、请求数、API Key/模型/分组明细；应通过独立校准口径合入统计。
- 余额校准不允许产生负余额；如果扣减后余额会小于 0，应拒绝本次校准并返回明确错误。
- Token 用量校准需要支持统计归属时间：默认归属今天，管理员可选择历史日期；统计查询按归属时间计入对应日榜、周榜和时间范围汇总。
- 校准记录需要同时保留归属时间和操作时间，避免历史统计口径与管理员审计口径混淆。
- 管理员可以在用户版使用记录页进入“代用户查看”模式，先选择目标用户，再查看与该用户自助页面一致的使用记录、汇总卡片和筛选体验。
- 选择用户入口应位于 API 密钥下拉栏左侧；选择目标用户后，API 密钥下拉栏应切换为该用户的 API Key 列表。
- 同一筛选行新增校准入口，校准目标默认为当前选中的用户；如未选择用户，应禁用或提示先选择用户。
- 校准入口打开表单时，需要支持 Token 用量调整、余额调整、统计归属日期和原因填写。
- 管理员代用户查看的普通使用记录明细仍不展示校准记录本身；校准只影响汇总/排行/统计口径。
- 用户选择入口、校准按钮、校准接口、校准审计记录均仅管理员可访问。
- 普通用户打开自己的使用记录页时，页面结构和交互保持现状，不出现管理员代看或校准相关控件。
- 普通用户接口返回中不得包含校准记录、校准原因、校准操作者或任何能暴露后台校准存在的字段。
- 校准表单支持两种输入模式：
  - 增减量模式：管理员直接填写 Token 用量或余额的正负向调整值。
  - 目标值模式：管理员填写目标 Token 用量或目标余额，系统按当前实际值自动计算差额。
- Token 目标值模式需要提供独立的计算范围选择，用于计算“当前实际 Token 用量”和目标值之间的差额；该范围与页面筛选范围可以不同。
- 页面筛选范围只决定管理员当前查看的使用记录，不能隐式决定目标值校准的计算范围。
- Token 校准计算出差额后，应按计算范围内每天原始 Token 用量占比分摊到各天；原始 Token 为 0 的日期不分摊，非 0 日期按比例分摊。
- Token 目标值模式下，如果计算范围内原始 Token 总量为 0，应拒绝校准并提示“该范围没有原始用量，无法按比例分摊”。
- 分摊结果需要计入对应日期的日榜、周榜、时间范围汇总和运营统计。
- 分摊过程需要保证所有日期分摊值求和等于本次校准差额；整数 Token 的舍入余数需要采用确定性规则处理。
- 无论使用哪种输入模式，审计记录都需要保存输入模式、输入值、计算前值、计算后值和实际差额。
- 审计记录还需要保存 Token 计算范围和按日分摊明细，便于解释历史统计变化。
- 余额目标值模式同样不得产生负余额；目标余额小于 0 或计算后余额小于 0 时应拒绝。

- [ ] 管理员可以完成 Token 用量和余额的正负向校准。
- [ ] 管理员可以追溯校准操作的操作者、目标用户、调整值、原因和时间。
- [ ] 校准后的 Token 用量会反映在用户侧汇总、管理员排行榜和运营统计中。
- [ ] 校准不会制造一条普通请求明细，用户无法从请求明细中看到校准原因或校准记录。
- [ ] 余额扣减校准在结果会低于 0 时失败，且不会写入部分校准记录。
- [ ] 管理员未指定归属时间时，Token 校准默认计入今天。
- [ ] 管理员指定历史归属日期时，Token 校准计入对应日榜、周榜和时间范围统计。
- [ ] 管理员审计记录可以区分“统计归属时间”和“实际操作时间”。

- [ ] 普通用户登录后看不到用户选择入口、校准按钮或任何校准相关文案。
- [ ] 普通用户不能调用管理员代看和校准接口；直接请求应返回权限错误。
- [ ] 普通用户侧使用记录、兑换历史、导出数据和响应字段中不出现校准明细或校准来源信息。
- [ ] 管理员可以选择增减量模式完成 Token/余额校准。
- [ ] 管理员可以选择目标值模式完成 Token/余额校准，系统自动计算并展示本次实际差额。

- [ ] 分摊后各日期 Token 校准量合计等于本次校准差额。
- [ ] 管理员审计记录包含输入模式、输入值、计算前值、计算后值和实际差额。
- [ ] 管理员审计记录包含 Token 计算范围和按日分摊明细。
- [ ] 校准行为不会破坏现有用量统计、余额计算和排行榜接口的一致性。

## Decision (ADR-lite)

**Context**: 用户希望校准 Token 用量和余额，同时不让普通用户看到校准记录；但如果校准不影响统计口径，用户侧汇总与后台结果会持续不一致。

**Decision**: Token 用量校准必须影响统计汇总、排行榜和运营统计；校准明细本身仅管理员可见，不进入普通用户请求明细或兑换历史。

**Consequences**: 实现上需要把“统计汇总可见”和“明细记录隐藏”拆开，避免直接复用 `usage_logs` 普通请求记录或 `redeem_codes` 普通兑换历史。

**Visibility Decision**: 管理员代看用户使用记录、选择用户入口、校准入口和校准审计能力全部限定为管理员可见；普通用户页面、普通用户接口和普通用户可导出的数据都不能暴露这些能力的存在。

**Allocation Decision**: Token 校准差额按管理员选择的计算范围内每天原始 Token 占比分摊到各日期，确保日榜、周榜、历史趋势和时间范围汇总都随历史用量结构同步修正。

**Zero Usage Decision**: Token 目标值模式下，如果计算范围内原始 Token 总量为 0，则拒绝校准，不降级为平均分摊或单日落点。

## Technical Approach

- 新增管理员专用校准模型/接口，独立记录 Token 与余额校准，不复用普通 `usage_logs` 请求记录或普通 `redeem_codes` 兑换历史。
- 在用户版使用记录页增加管理员模式控件：用户选择在 API Key 下拉左侧，校准入口在同一筛选行；普通用户页面保持现状。
- 管理员代看使用管理员专用接口按目标用户查询，但前端展示复用用户视角字段和表格口径。
- Token 校准写入独立校准记录与按日分摊明细；统计查询在汇总层合并真实用量与校准分摊，普通请求明细仍只展示真实请求。
- 余额校准直接影响用户余额，但审计记录与普通用户兑换历史隔离；任何会导致负余额的校准都拒绝。

- 现有管理员余额调整入口为 `POST /api/v1/admin/users/:id/balance`，会更新 `users.balance`，并创建 `type=admin_balance` 的 `redeem_codes` 记录。

- 现有 Token 用量和排行榜主要从 `usage_logs` 聚合；直接插入校准型 `usage_logs` 会进入用户使用记录、请求数、模型/API Key/分组明细和排行榜。
- 用户表目前有 `balance`、`total_recharged` 等余额相关字段，没有看到独立的累计 Token 用量字段；Token 用量校准需要明确是进入统计口径、独立校准口径，还是仅作为余额修正依据。
- 用户版使用记录页面为 `frontend/src/views/user/UsageView.vue`，当前筛选行包含 API Key 下拉、时间范围和操作按钮。
- 用户版 `/usage` 接口强制使用当前登录用户 ID；管理员代用户查看不能直接给该接口传 `user_id`，需要管理员专用接口或管理员模式适配。
- 管理员使用记录页已有用户搜索和 API Key 搜索能力，但它是管理员宽表视图，不等同于“用户看到的一样”。
- 现有管理员接口 `/api/v1/admin/usage/search-users` 与 `/api/v1/admin/usage/search-api-keys?user_id=...` 可复用为用户选择与目标用户 API Key 下拉的数据源。
