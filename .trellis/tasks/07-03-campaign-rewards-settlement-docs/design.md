# 活动邀请奖励与结算系统设计

## 1. 设计目标

本设计用于实现“邀请好友赢奖金——限时邀请排行榜活动”的首期闭环。系统需要在不污染现有全局邀请返利逻辑的前提下，新增独立活动模块，支持活动配置、有效邀请统计、动态奖金池、排行榜奖励、贡献奖励、审核冻结、结果公示和后台一键发放到账户余额。

首期重点是跑通运营闭环：配置活动 → 用户邀请 → 被邀请用户注册/充值达标 → 实时预估榜单与奖金池 → 活动结束冻结 → 审核修正 → 最终结算 → 公示 → 一键发放。

## 2. 核心边界

- 活动模块独立于现有普通邀请返利配置，不复用 `affiliate_enabled` 作为活动开关。
- 邀请关系可复用现有用户邀请绑定关系，但活动内必须保存快照，避免后续用户资料或全局配置变化影响历史活动。
- 支付、兑换码、余额变动可复用现有底层能力，但活动需要独立记录入池、奖励计算和发放批次。
- 首期不接入真实提现、外部打款、银行转账、支付平台转账或兑换码核销，统一一键发放到账户余额。
- 首期不设置单用户奖励上限。

## 3. 领域模型

### 3.1 活动

活动是所有配置、统计、结算和发放的聚合根。

建议字段：

- `id`：活动 ID。
- `name`：活动名称。
- `description`：活动说明。
- `cover_url`：活动封面。
- `rules_text`：活动规则文本。
- `status`：草稿、预热中、进行中、审核中、公示中、待发放、已发放、已取消、提前终止。
- `warmup_start_at`：预热开始时间。
- `start_at`：正式活动开始时间。
- `end_at`：正式活动结束时间。
- `audit_start_at` / `audit_end_at`：审核期。
- `publicity_start_at` / `publicity_end_at`：公示期。
- `payout_due_at`：计划发放时间。
- `created_by` / `updated_by`：操作人。
- `created_at` / `updated_at`。

### 3.2 活动配置版本

配置版本用于保存活动规则快照。活动发布后，排行榜/贡献池比例、奖励人数、名次权重、最低发放金额、发放方式和发放渠道冻结；活动开始后只允许有效充值门槛和动态注入比例生成新版本，不追溯历史行为。

建议拆出配置版本：

- `campaign_id`：活动 ID。
- `id`：配置版本 ID。
- `version`：版本号。
- `version_scope`：发布快照、门槛调整、注入比例调整。
- `effective_at`：生效时间。
- `recharge_threshold_cents`：有效充值门槛，首期默认 20 元。
- `allow_accumulated_recharge`：是否允许累计充值达标。
- `pool_injection_rate`：动态奖金池注入比例，首期默认 10%。
- `rank_pool_ratio`：排行榜奖励池比例，固定 80%。
- `contribution_pool_ratio`：贡献奖励池比例，固定 20%。
- `rank_reward_count`：排行榜奖励人数，默认 Top10。
- `rank_weights_json`：名次权重，默认 `30/20/15/10/8/6/4/3/2/2`。
- `min_payout_amount_cents`：最低发放金额，默认建议 1 元。
- `change_reason`：版本调整原因。
- `created_by` / `created_at`。

- `invitee_user_id`。

### 3.11 金额字段规范

- 活动相关账务字段统一以整数最小货币单位存储，默认人民币分。
- 百分比、平方根和奖励分摊使用高精度 Decimal 中间值。
- 单用户最终发放金额向下取整到分。
- 取整尾差、低于最低发放金额未发放金额统一记录为奖金池回收，不再二次分配。
- 对接现有余额服务时，如现有余额事实源不是整数分，只能在发放边界做一次显式单位转换，并保存转换前后快照。

## 4. 核心流程

### 4.1 活动创建与发布

1. 管理员创建活动草稿。
2. 配置活动时间、活动规则、有效充值门槛、初始奖金池、动态注入比例、奖励配置。
3. 系统校验奖励比例合计为 100%、Top10 权重合计为 100%、时间区间合法、最低发放金额大于等于 0、同一时间不存在其他进行中活动。
4. 管理员发布活动，活动进入预热中或进行中。
5. 活动发布时冻结奖励分配规则；活动开始后如需调整，只允许门槛或动态注入比例生成新配置版本。

### 4.2 邀请与达标

1. 用户通过活动页复制邀请码或邀请链接。
2. 被邀请人通过邀请链接或邀请码注册。
3. 系统记录活动邀请关系、门槛快照和归因来源。
4. 被邀请人充值或兑换。
5. 系统累计被邀请人在活动期内的有效充值金额。
6. 达到门槛后，邀请记录进入待审核或已生效状态，并更新邀请人的实时预估数据。

### 4.3 奖金池注入

1. 被邀请用户产生有效充值。
2. 系统判断充值是否属于活动被邀请用户、支付成功或兑换成功时间是否落在活动期内、是否真实有效、是否非赠送/非手动赠额。
3. 系统按配置版本快照计算入池金额：有效充值金额 × 10%。
4. 入池记录先进入待确认，风控/退款观察期结束后转为已确认。
5. 退款、冲正、撤销兑换或风控拒绝时，写入奖金池扣减明细，并同步更新有效充值与充值入池记录的聚合扣减金额。

### 4.4 实时榜单与预估奖励

1. 系统按有效邀请人数生成实时预估榜单。
2. 并列排序依次使用被邀请用户累计有效充值金额、达到当前有效邀请人数时间、参与活动时间。
3. 奖金池使用预计总奖金池进行预估展示。
4. 页面标注预估数据不代表最终结算。

### 4.5 结束冻结与审核

1. 活动结束时间到达后，活动进入审核中。
2. 系统冻结结束时预估排行榜。
3. 冻结后不再接受新的注册、充值或邀请记录进入活动统计；活动结束时仍未支付成功、未兑换成功或未充值到账的订单不进入本期待审核。
4. 审核处理退款、冲正、撤销兑换、异常邀请码注册、批量注册、自邀、测试账号、内部账号等。
5. 审核完成后重新计算最终有效邀请、最终奖金池和最终奖励。

### 4.6 结果公示与发放

1. 系统生成最终结算快照。
2. 管理员确认后进入公示期。
3. 公示内容脱敏展示最终奖金池、前十名名单、有效邀请人数、奖励金额、活动参与数据和发放时间。
4. 公示结束后，管理员一键发放到账户余额。
5. 发放批次记录成功、失败、跳过和重试状态。

### 4.7 发放后退款与追偿

1. 最终结算前发生退款、冲正或撤销兑换时，直接重新计算有效邀请、奖金池和奖励。
2. 最终结算后、发放前发生退款或冲正时，活动退回审核中或重新生成最终结算快照。
3. 发放后发生退款或冲正时，不修改历史排行榜和原发放批次。
4. 系统生成发放后追偿记录，记录原奖励、需追偿金额、关联退款/冲正来源、幂等键和处理状态。
5. 追偿经后台审核后优先从用户余额扣回；扣回必须幂等，并记录扣回前后余额快照、余额流水 ID、错误信息和处理时间。
6. 余额不足时保留待追偿金额，并限制相关账号参与后续活动或进入人工处理。

## 5. 奖励计算

### 5.1 奖金池

```text
最终奖金池 = 初始奖金池 + 有效充值注入金额 - 退款及异常订单对应扣减金额
动态奖金注入金额 = 被邀请用户有效充值金额 × 10%
```

### 5.2 排行榜奖励

```text
排行榜奖励池 = 最终奖金池 × 80%
第 N 名奖励 = 排行榜奖励池 × 第 N 名权重
```

默认 Top10 权重：

- 第 1 名：30%
- 第 2 名：20%
- 第 3 名：15%
- 第 4 名：10%
- 第 5 名：8%
- 第 6 名：6%
- 第 7 名：4%
- 第 8 名：3%
- 第 9 名：2%
- 第 10 名：2%

### 5.3 贡献奖励

```text
贡献奖励池 = 最终奖金池 × 20%
个人贡献权重 = √个人有效邀请人数
个人贡献奖励 = 贡献奖励池 × 个人贡献权重 ÷ 所有参与用户贡献权重之和
```

进入排行榜前十名的用户也可同时获得贡献奖励。

### 5.4 最低发放金额

```text
若用户最终奖励 < 最低发放金额：
  final_payout_amount = 0
  withheld_amount = 用户最终奖励
  withheld_reason = 低于最低发放金额未发放
```

低于最低发放金额的奖励不发放，并回收到奖金池。

### 5.5 取整与尾差

```text
单用户最终发放金额 = floor(单用户总奖励金额, 分)
取整尾差 = 单用户总奖励金额 - 单用户最终发放金额
最终奖金池 = 实际发放总额 + 低额回收金额 + 取整尾差 + 其他未发放回收金额
```

尾差和低额回收只回收到奖金池，不参与二次重分配。

## 6. 页面设计

### 6.1 用户端

- 活动首页：活动信息、预计总奖金池、初始奖金池、有效充值门槛、邀请码/邀请链接、复制按钮、规则入口、奖励说明、排行榜入口、我的邀请记录入口。
- 我的数据：有效邀请、待审核邀请、无效邀请、当前排名、预计排名奖励、预计贡献奖励、总预计奖励、距离上一名/前十名差距、被邀请用户累计充值。
- 邀请记录：被邀请用户脱敏昵称、注册时间、门槛快照、累计充值、状态、达标时间、未达标差额、无效原因。
- 排行榜：前 50 名、当前用户排名、有效邀请人数、被邀请用户累计充值金额、当前预计奖励、榜单更新时间。

### 6.2 管理后台

- 活动列表：状态、时间、参与人数、奖金池、待审核数量、发放状态。
- 活动配置：基础信息、时间配置、规则文本、封面、状态管理。
- 邀请规则：有效充值门槛、门槛版本、累计充值、邀请有效期、参与/排除范围。
- 奖金池：初始奖金、追加奖金、动态注入比例、奖金池上限、确认/待确认/扣减明细、调整记录、奖金池层补偿记录。
- 奖励配置：80%/20%、Top10、名次权重、最低发放金额、计算预览。
- 用户级奖励调整：补发、扣回、人工修正、计入结算状态和补发批次。
- 数据看板：参与人数、邀请人数、有效邀请、待审核、无效邀请、注册、付费、充值流水、奖金池趋势、排行榜、转化率、人均邀请。
- 审核结算：待审核邀请、异常记录、冻结榜单、最终结算、结果公示。
- 发放记录：发放批次、明细、失败重试、余额快照。

## 7. 风控与审计

- 所有奖金池调整、配置版本变更、邀请审核、奖励计算、结果确认、发放批次必须记录操作人、时间和原因。
- 邀请记录、入池记录、奖励结果必须保存对应的 `config_version_id`，保证门槛、注入比例和发布时冻结奖励规则可追溯。
- 同一 IP 不能作为唯一作弊判定依据。
- 风险等级：低风险直接计入，中风险待审核，高风险暂不计入，确认违规判定无效并限制参与。
- 处罚规则需提前在活动说明中公示。
- 发放必须使用幂等键，避免重复发放。

## 8. 非目标

- 不接入提现或外部打款。
- 不将活动规则写入现有全局邀请返利配置。
- 不默认纳入全平台充值。
- 不做历史活动回填。
- 不在本阶段实现高级自动风控模型，只保留风险维度、状态与人工审核入口。
