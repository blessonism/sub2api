# campaign rewards admin lifecycle optimization

## Goal

优化邀请活动管理端，让管理员能够安全处理活动生命周期，优先补齐删除/归档遗漏，并改善列表操作、状态表达和误操作防护，避免破坏参与记录、结算记录与已发奖励审计链路。

## What I already know

- 用户指出：管理员在邀请活动中无法删除活动，这是当前遗漏。
- 邀请活动涉及用户参与、奖励结算和发放，删除能力必须区分无数据活动与已有业务数据活动。
- 当前分支已有活动奖励相关未提交改动，实施时必须保护既有改动，不做无关回滚。
- 本仓库是下游二开仓库，任务必须以 `custom/main` 为目标基线，并遵守下游 fork 工作流。

## Assumptions (temporary)

- 管理端已有活动列表/编辑页面，优先在现有页面补操作，不新建大规模后台模块。
- 如果活动已有参与或结算数据，默认采用归档/下架等软删除语义；仅无参与数据的活动可硬删除。
- 第一阶段不做复杂风控模型，只补关键生命周期动作和清晰状态提示。

## Requirements (evolving)

- 管理员可对邀请活动执行安全删除或归档操作。
- 删除/归档前展示影响范围与确认提示。
- 管理端列表应清晰展示活动状态，并提供符合状态的操作入口。
- 后端必须防止删除已有参与、结算或奖励发放记录的活动。
- 用户端不应展示已归档/已删除活动。

## Acceptance Criteria (evolving)

- [ ] 管理端活动列表提供删除/归档入口，并按活动状态或数据依赖禁用高风险动作。
- [ ] 后端删除接口具备权限、存在性和业务依赖校验。
- [ ] 有参与/结算/奖励记录的活动不能被硬删除，返回明确错误。
- [ ] 无参与数据的活动可删除，列表刷新后不再展示。
- [ ] 相关前端状态文案与中英文 i18n 完整。
- [ ] 覆盖后端服务/接口或前端工具的关键测试。

## Out of Scope

- 不在本任务中重做完整活动创建向导。
- 不在本任务中实现复杂反作弊、批量导出或新结算算法。
- 不处理生产数据库迁移或线上数据清理。
