# brainstorm: 手动调整邀请活动榜单

## Goal

为邀请活动管理端增加手动调整能力，让管理员在活动数据出现误判、风控复核、人工补录、纠错或运营补偿时，可以通过“邀请记录修正 + 榜单分数覆盖”影响榜单与结算结果，同时保留轻量操作痕迹，方便事后解释。

## What I already know

* 用户希望“能够手动调整榜单”。
* 当前榜单不是独立可编辑表，而是从 `campaign_invite_records` 聚合生成。
* 现有排序规则为：有效邀请数降序、受邀用户有效充值金额降序、达标时间升序、加入时间升序。
* 有效邀请来自邀请记录状态 `effective`；低于门槛的邀请为 `recharge_unqualified`，未充值/复核中等状态不会计入有效邀请数。
* 管理端已有活动生命周期操作：冻结榜单、预览结算、最终结算、派奖。
* 活动已有奖池手动调整能力，但它只影响奖金池金额，不影响用户榜单排名。
* 用户确认希望同时支持“修正邀请记录”和“覆盖榜单分数”两种能力。
* 用户确认审计不需要很严格，保留轻量原因/操作人/时间即可。
* 用户确认榜单分数覆盖采用“加减增量”方式，不直接设置最终数值。
* 用户确认手动调整允许到派奖前；最终结算后仍可调整，但调整后必须重新最终结算，派奖后锁定。

## Assumptions (temporary)

* “手动调整榜单”的动机同时包含纠错、人工复核和运营补偿。
* 调整可作用于派奖前；已经最终结算但未派奖的活动调整后需要重新生成最终结算。
* 审计粒度以轻量追溯为主，不做复杂审批流、复核流或不可篡改审计账本。

## Open Questions

* 暂无阻塞问题；下一步可进入实现设计。

## Requirements (evolving)

* 管理员可以查看某个活动下邀请人的榜单与邀请明细。
* 管理员可以修正某条邀请记录的状态、有效充值金额和备注，让它影响对应邀请人的有效邀请数与充值金额。
* 管理员可以通过增量方式调整邀请人的榜单分数，例如人工 `+2/-1` 有效邀请数或 `+10000/-5000` 分有效充值金额，用于不方便落到具体受邀用户的场景。
* 榜单分数覆盖不支持直接设置最终值，只记录并叠加增量。
* 管理员执行调整时填写可选或简短原因，并记录操作人和操作时间；不引入复杂审批。
* 手动调整允许到派奖前；如果已经生成最终结算，调整后必须让最终结算失效或要求重新最终结算，避免旧结算结果继续派奖。
* 已派奖活动不可再调整。
* 调整后榜单、冻结快照、预览结算和最终结算应使用一致的数据来源。
* 榜单展示需要能标识某个用户存在手动覆盖，避免管理员误以为全部来自自然邀请记录。
* 重复操作、撤销/反向调整、低于 0 的金额或有效邀请数等边界需要明确处理。

## Acceptance Criteria (evolving)

* [ ] 管理员可以将某条邀请记录标记为有效/无效/待复核，并影响对应邀请人的有效邀请数。
* [ ] 管理员可以修正该邀请记录的有效充值金额，金额达到门槛时能计入有效邀请。
* [ ] 管理员可以对某个邀请人进行榜单分数增量调整，影响榜单排序与奖励计算。
* [ ] 系统不提供直接设置最终有效邀请数或最终有效充值金额的入口。
* [ ] 调整记录操作人、操作时间和简短原因；原因不需要走强制审批。
* [ ] 榜单接口和管理端 UI 可以识别/展示存在手动覆盖的榜单行。
* [ ] 榜单 API、冻结快照、奖励预览、最终结算使用调整后的结果。
* [ ] 最终结算后未派奖时仍可调整，但调整会让旧最终结算不可用于派奖，管理员需要重新最终结算。
* [ ] 已派奖活动不可继续调整。

## Out of Scope (explicit)

* 不在本任务内处理生产数据迁移或真实线上活动手工改数。
* 不默认支持已派奖后的自动追缴/补发，除非后续需求明确。
* 不把奖池金额调整与榜单调整混为一个入口；奖池已有独立调整能力。
* 不做复杂审批、复核、不可篡改审计日志或多管理员确认。
* 不支持直接固定排名；排名仍由调整后的有效邀请数、充值金额和现有排序规则计算得出。
* 不支持直接设置某个邀请人的最终榜单数值；本任务只支持增量调整。

## Decision (ADR-lite)

**Context**: 现有榜单由邀请记录聚合生成，但运营上存在无法对应到单条邀请记录的补偿/纠偏需求。

**Decision**: 同时支持两层调整：一是修正具体邀请记录；二是对邀请人的榜单分数做手动增量调整。增量调整可正可负，但不允许直接设置最终值。调整允许到派奖前；最终结算后未派奖仍可调，但必须重新最终结算。审计采用轻量记录，包含操作人、时间和原因，不引入复杂审批。

**Consequences**: 邀请记录修正保持数据解释性；榜单分数增量调整提供运营灵活性。代价是榜单行需要明确标识手动调整，并确保结算链路使用同一套调整后数据。实现上还需要保护派奖入口，避免使用调整前的旧最终结算结果。
