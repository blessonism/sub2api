# 一次性抽奖活动

## 背景

当前抽奖活动已有 `draw_schedule_type=single`，但后端的达标统计窗口仍按开奖日自然日计算，导致“单次定时开奖”在用户体感上仍像周期抽奖。用户希望抽奖可以配置为真正的一次性活动：活动期间累计 Token 达标，最终只开奖一次。

## 目标

- 复用现有 `single` 调度类型表达一次性抽奖，不新增数据库字段。
- 一次性抽奖的达标统计窗口为活动 `start_at` 到 `draw_at`，而不是开奖日当天。
- `daily_once` 模式在一次性抽奖里表示整个活动期间达标后获得一次抽奖资格。
- `stepped` 模式在一次性抽奖里按整个活动期间累计 Token 计算抽奖次数。
- 日抽奖 `daily` 的现有自然日窗口行为保持不变。
- 前端用户侧文案能区分 daily 的“今日”与 single 的“累计/活动累计”语义。

## 非目标

- 不引入新的开奖周期类型或迁移表结构。
- 不改变 `entry_date` / `draw_date` 作为开奖批次日期键的存储方式。
- 不改变排行榜或其他活动类型的统计窗口。

## 实现约束

- 对 single：`entry_date` / `draw_date` 继续使用 `draw_at` 所在日期，避免影响现有唯一索引与开奖批次。
- 对 single：候选人同步、用户达标检查、报名检查都使用活动开始到开奖时间的累计窗口。
- 对 daily：保持从开奖日期自然日开始，到当前时间或开奖时间截止的窗口。
- 保持 API 响应兼容；如复用 `today_tokens` 字段，前端根据 `draw_schedule_type` 改展示标签。

## 验收标准

- 一次性抽奖在开奖日前任意时间展示的是活动累计 Token 和累计达标进度。
- 一次性抽奖手动同步/开奖时，候选人来自活动开始到开奖时间的累计用量。
- 日抽奖仍只统计当天窗口。
- 覆盖后端 single/daily 窗口差异测试，前端相关测试与类型检查通过。
