# OVH Sub2API 502 只读排障设计

## 边界

排查覆盖四层：公网入口/CDN、源站反向代理、Sub2API 应用、外部上游。所有命令必须是只读的，并限制日志时间窗口和输出量。禁止读取容器环境变量全文或请求正文。

## 证据流

1. 本地解析 `ssh ovh` 的实际目标和连接参数，不展示密钥内容。
2. 远端采集宿主机资源、容器状态、健康、重启和资源限制快照。
3. 识别监听端口、反向代理容器及其挂载的配置文件，再读取与代理行为相关的配置片段。
4. 在反向代理和应用日志中搜索样例 request id；无命中时，使用近期有限窗口的 502、超时和上游失败样本。
5. 将日志时间、状态码、错误文本和配置值交叉验证，判断 502 的生成层和放大因素。

## 安全控制

- 不运行构建、部署、重启、重载、写文件、数据库命令或容器变更命令。
- 不执行 `docker inspect` 的完整环境变量输出；仅选择状态、健康、重启策略、资源限制和挂载路径字段。
- 日志使用 `--since`、`--tail` 和关键词过滤，避免全量扫描影响生产。
- 不调用需要 Authorization 的 `/responses`；只允许无敏感数据的本地健康检查。
- 输出中对疑似凭据、URL 查询参数和用户标识做脱敏。

## 判断框架

- 根因：直接生成 502 或导致上游请求失败的事件。
- 放大因素：超时不匹配、无重试、连接池耗尽、流式缓冲、资源限制等使错误更频繁或更难恢复的配置。
- 可观测性缺口：缺少 request id 贯穿、上游状态码被统一包装、日志保留过短等妨碍定位的问题。

## 变更与回滚

本任务不实施生产变更，因此无运行时回滚步骤。任何整改都必须在报告后单独获得明确确认，并说明影响范围和回滚方式。
