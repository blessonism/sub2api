# 技术设计：抽奖活动常驻展示与中奖名单公开

## 1. 设计边界

复用现有 `is_featured` 作为“管理员当前指定的常驻抽奖活动”，不新增数据库字段或迁移。系统仍只允许一场活动被标记；设置新活动时沿用现有事务，先清除旧标记再设置新标记。

## 2. 后端可见性

- 管理员设置常驻时，活动必须为 `published`，但不再要求当前时间位于 `start_at` 与 `end_at` 之间。
- 用户活动入口优先返回 `published + is_featured` 的活动，不受时间窗口限制；不存在常驻活动时，继续回退到当前有效的已发布活动。
- 用户侧活动详情、公开中奖名单和参与者接口统一复用公开可见性规则：当前有效的已发布活动，或已发布且常驻的活动。
- 报名与资格写入仍由 `lotteryCampaignAcceptsEntries` 控制。结束后的常驻活动只能读取，不能报名或新增资格记录。
- `draft`、`cancelled`、`archived` 即使遗留 `is_featured` 标记也不对用户公开。

## 3. 中奖数据契约

中奖结果继续以 `lottery_winners` 为唯一事实来源，不复制到活动表。

- 用户端沿用公开 DTO：`masked_email`、`prize_name`、`reward_amount_cents`、`created_at`，只返回成功发放记录。
- 管理端新增活动级中奖列表调用，复用现有 `LotteryWinner` 管理 DTO，展示用户 ID、奖项、金额、状态、中奖/处理时间及失败信息。
- 管理端列表直接按活动查询全部中奖记录，不要求管理员先理解或选择开奖批次；已有批次级接口继续保留。

数据流：`lottery_winners` -> repository 查询 -> service 可见性/权限边界 -> admin/public handler -> typed frontend API -> 管理详情/用户活动组件。

## 4. 前端交互

- 管理端将“设为活动中心展示”调整为常驻语义，已结束但仍为 `published` 的活动也可操作。
- 选中活动后加载活动级中奖名单，在详情区域展示加载、空、成功和失败状态；切换活动时清空旧数据，防止串榜。
- 用户端已有“最近中奖”和“我的中奖”区域，后端放宽常驻活动可见性后继续复用；已结束状态隐藏报名动作并展示开奖结果。
- 中英文下游 locale overlay 同步更新常驻操作和中奖名单文案。

## 5. 兼容与风险

- 无数据库迁移，历史 `is_featured` 记录自动获得常驻语义。
- 未设置常驻活动时，当前有效活动的选择逻辑保持不变。
- 删除、取消常驻活动后不会继续公开；后续活动不会自动抢占常驻位置。
- 回滚只需恢复查询和服务规则，数据结构不受影响。
