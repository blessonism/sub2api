# 候选映射自动跟随上游 Key 当前分组

## Goal

上游倍率监控候选映射应以已绑定 API Key 在上游当前所属的分组为准，避免管理员手动填写的 `upstream_group_id` 在上游调整 Key 分组后过期，导致用量和倍率监控落到错误分组。

## Confirmed facts

- 候选已保存 `upstream_api_key_id`，但当前 `/api/v1/keys` 选项只返回 Key 的 ID、名称和脱敏值，不返回当前分组。
- 后端 `fetchUpstreamGroupUsageForDate` 按候选保存的 `upstream_group_id` 聚合绑定 Key 的用量；Key 当前所属分组变化时仍会写入旧分组。
- 前端候选表单同时要求选择 API Key 和手动填写/选择 `upstream_group_id`。
- 候选分组快照来自 `/api/v1/groups/available`，可用于校验上游当前分组是否存在。
- 当前仓库是 `Wei-Shaw/sub2api` 的下游二开仓库；任务基线应为 `custom/main`，工作分支为 `fix/upstream-relay-candidate-auto-key-group`。

## Requirements

- 从上游 Key 列表读取并返回该 Key 当前所属的分组 ID，必要时同时返回分组名称。
- 候选监控刷新时按 Key 当前分组聚合用量，不再以过期的手动分组作为唯一归属依据。
- 候选表单选择 API Key 后自动带出其当前分组；手动分组输入仅作为上游 Key 无分组信息或历史数据兼容的回退。
- 保留已有候选数据和 API 契约的兼容性；未知/缺失当前分组时给出明确的监控问题，不得静默写入错误分组。
- 不改变倍率计算规则、候选 Key 绑定关系或生产数据，不执行数据库迁移。
- 候选列表和推荐输入必须使用 Key 当前分组对应的快照；候选保存的分组只作为配置/历史回退，不得在换组后继续驱动当前推荐。
- 历史日期定格不得使用 Key 今天的分组覆盖过去日期归属；历史刷新继续使用候选保存的分组。
- 同一上游 Key 即使被多条候选重复绑定，也只能累计一次完整用量。

## Acceptance Criteria

- [x] `/connectors/:id/api-keys` 返回的 Key 选项包含当前分组信息（若上游响应提供）。
- [x] 绑定 Key 的用量刷新在 Key 换组后归属新分组，旧手动分组不再接收该 Key 的新用量。
- [x] 前端选择 Key 后自动回显当前分组；历史候选仍可编辑和保存。
- [x] 上游 Key 响应缺少分组或无法归属时，返回稳定的 issue/error 信息并保留其他 Key 的刷新结果。
- [x] 增加后端解析/聚合测试和前端表单回显测试，相关类型检查通过。
- [x] Key 换组后候选列表和推荐读取新分组快照，且不自动改写候选数据库配置。
- [x] 历史日期刷新使用保存的分组，不受 Key 当前分组变化影响。
- [x] 重复绑定同一 Key 时用量只累计一次。

## Resolved scope decision

- 刷新时只动态使用解析出的当前分组，不自动改写候选的 `upstream_group_id`；这样后台刷新不会悄悄改变管理员保存的配置和历史映射。管理员打开编辑并保存时，前端可将当前分组显式写回。
