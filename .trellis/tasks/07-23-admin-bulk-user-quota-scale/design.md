# 管理员批量缩减用户余额 - 技术设计（调查稿）

## 边界

- 入口放在管理员用户管理页，作用范围固定为全部未软删除用户，包含管理员和已禁用用户。
- 目标字段只有 `users.balance` 钱包余额；不修改 `total_recharged`、冻结余额、Token 用量、平台窗口额度、订阅额度或历史充值订单。
- 管理员输入缩减倍数 `x > 1`，目标余额为 `旧余额 / x`。
- 预览与执行应属于同一管理员用户管理 API 模块，不复用余额汇总页面的排除用户口径。

## 数据流

1. 前端输入 `x`，先做正数、大于 1、有限数校验。
2. 前端调用只读预览接口；后端在数据库中按未软删除条件计算用户数、当前余额总额、按数据库精度计算的目标总额和减少总额。
3. 管理员在确认弹窗核对预览，前端生成幂等键并调用执行接口。
4. 后端幂等协调器先锁定请求；同一幂等键重放原响应，不再次执行。
5. 执行事务中以数据库原子表达式更新所有 `deleted_at IS NULL` 用户的余额，并返回每行修改前/后值。
6. 同一事务为实际发生变化的用户写入 `admin_balance` 调整记录，备注包含批量操作标识和缩减倍数；任意失败整体回滚。
7. 提交后统一失效受影响用户的认证缓存和计费余额缓存，返回操作标识、用户数、总额变化和舍入说明。

## 精度与并发

- `users.balance` 是 `decimal(20,8)`，计算必须在 PostgreSQL numeric 语义中完成，避免 Go `float64` 先读后写造成精度或丢更新。
- 因子允许有限小数，最多 8 位小数；应以 decimal 文本传给数据库并显式转换为 numeric，最终值按字段 8 位小数落库。
- 原子批量更新以行锁串行化于并发扣款，不会出现先读后写覆盖；不同用户的锁获取可能与并发扣款交错，但每个用户的结果仍是合法串行结果。
- 预览和执行之间余额可能变化，因此执行响应必须以执行事务实际结果为准，不能承诺与预览完全相同。

## 审计与恢复

- 沿用现有 `admin_balance` 历史记录，使每个用户都能在余额历史中看到负向调整。
- 需要有批量操作标识，至少写入 notes；若后续需要独立查询或撤销，再增加专用批次表或可检索的 operation id。
- 不建议用“再次乘以 x”恢复：后续充值、消费和小数舍入会使反向操作不准确。第一版应保留批次标识和逐用户 delta，人工恢复时按原 delta 加回，才能保留其后的充值/消费。

## 失败、幂等与回滚

- 预览接口不写数据库。
- 执行事务全成全败；审计记录写入失败也必须回滚余额。
- 幂等键绑定倍数和操作参数，复用现有管理员幂等 JSON 工具；同键不同参数返回冲突。
- 进程在提交后、缓存失效前崩溃时，余额已提交但缓存可能短暂陈旧；缓存失效需要记录失败，并由缓存 TTL 最终收敛。

## 取舍

- 不按页面分页循环调用单用户余额接口：这会放大请求数、产生部分成功窗口并难以保证统一审计。
- 不新增“全局额度”字段或修改历史充值金额：计费余额是当前钱包状态，历史充值是统计口径。
- 第一版不新增自动撤销能力；优先复用 operation id + notes 关联逐用户余额历史，只有需要独立的批次历史页面时再引入专用批次表。
