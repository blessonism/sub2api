# 管理员批量缩减用户余额

## Goal

为管理员提供一个按统一倍数批量缩减用户钱包余额的安全入口，以便调整中转站计费口径，同时保证操作范围明确、金额计算准确、执行幂等且全程可追溯。

## Background

- 用户钱包余额存储在 `users.balance`，PostgreSQL 类型为 `decimal(20,8)`，直接参与中转站计费扣款。
- 管理员用户页已有单用户余额设置、增加、扣减和余额历史，但没有全量按倍数缩减入口。
- 现有单用户余额链路会拒绝负余额、失效认证与计费缓存，并写入 `admin_balance` 调整记录。
- Token 用量校准、平台窗口额度、订阅额度和冻结余额是独立对象，不属于本次调整范围。

## Requirements

- 操作对象固定为全部未软删除用户的 `users.balance`，包含管理员和已禁用用户。
- 管理员输入有限小数倍数 `x > 1`，最多 8 位小数，新余额按 `旧余额 / x` 计算。
- 余额结果按现有 `decimal(20,8)` 精度落库；零余额保持为零，结果不得为负数。
- 执行前提供只读预览，展示目标用户数、当前余额总额、缩减后余额总额和预计减少金额。
- 预览不能作为写入快照；正式执行时后端必须基于当时数据库余额重新计算，并返回实际结果。
- 二次确认必须明确作用于全部未软删除用户，并明确包含管理员和已禁用用户。
- 正式执行必须使用幂等键；重复提交同一请求只执行一次，同一幂等键绑定不同参数时返回冲突。
- 所有用户余额更新和逐用户 `admin_balance` 调整记录必须在同一事务中全成全败。
- 批量计算必须在数据库中原子执行，不能用前端预览值或 Go 层先读后写覆盖并发消费/充值。
- 事务提交后必须失效受影响用户的认证缓存和计费余额缓存，并记录失效失败以便排查。
- 每次执行必须生成可检索的 `operation_id`，写入逐用户调整记录，保留调整前后值或等价 delta，支持人工核对和恢复。
- 第一版不提供自动撤销按钮；恢复时按原负向 delta 加回，避免覆盖操作后的正常消费或充值。

## Acceptance Criteria

- [ ] 空值、非有限数、`x <= 1` 或超过 8 位小数的输入在前后端均不能执行。
- [ ] 预览仅统计未软删除用户，包含管理员和已禁用用户，并正确返回四项汇总数据。
- [ ] 确认弹窗明确显示倍数、目标范围和预览汇总。
- [ ] 执行时按当前余额重新计算，响应返回实际影响用户数和实际总额变化。
- [ ] 执行后每个未软删除用户的余额等于其执行时余额除以 `x` 后按 8 位小数落库的结果。
- [ ] 软删除用户、`total_recharged`、冻结余额、Token 用量、平台额度和订阅额度保持不变。
- [ ] 任一余额更新或审计记录写入失败时，所有余额和记录均回滚。
- [ ] 并发消费或充值不会被批量操作的陈旧读值覆盖。
- [ ] 同一幂等键重复提交不会二次缩减；同键不同参数返回冲突。
- [ ] 用户余额历史能看到本次负向调整，并能通过 `operation_id` 关联到同一批次。
- [ ] 操作成功后用户列表刷新，缓存最终与数据库余额一致。

## Out of Scope

- 不修改软删除用户、历史充值总额、冻结余额、Token 用量、平台窗口额度、订阅额度或充值订单。
- 不支持按筛选结果、选中用户、角色或状态缩减。
- 不提供后台任务、进度轮询、定时执行或自动撤销按钮。
- 不用“再次乘以 x”恢复余额；需要恢复时按批次逐用户 delta 人工处理。
