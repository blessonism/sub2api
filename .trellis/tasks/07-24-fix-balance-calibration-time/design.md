# 余额校准时间归属设计

## Boundary

复用 `admin_usage_calibration_daily_allocations` 作为校准统计的唯一按日归属表，新增 `balance_delta NUMERIC(18,6)`。审计主表继续保存整笔余额差额与操作时间，用户余额更新流程不变。

## Data Flow

1. 同一请求包含 Token 与非零余额校准时，使用 Token 范围内各日 `original_tokens` 作为权重。
2. 将余额差额转换为百万分之一美元的整数单位，复用最大余数法按日分摊，再写入每日分摊行。
3. 余额消费统计优先汇总每日分摊中的负值；没有每日余额分摊的 balance-only 记录继续按主表 `created_at` 汇总。
4. 总计查询和日期范围查询走同一组合 SQL，避免同一记录同时从日表与主表重复计入。
5. 消费校准请求携带独立日期范围；仓储事务汇总原始 `usage_logs.actual_cost` 与已有校准差额，计算消费差额后反向更新钱包。
6. 消费校准的模式、输入值、范围计算前后值和实际差额写入独立审计字段；钱包前后值继续写入现有余额字段。

## Contracts

- 每笔日余额差额精度为 6 位小数，逐日合计严格等于主表 `balance_delta`。
- 权重余数相同时依次按原始 Token 较大、日期较早排序，结果可复现。
- 正向余额差额会写入日分摊用于完整审计，但消费统计仍只累计负向差额。
- Token 差额为零但请求同时包含余额校准时，仍保留 Token 日期和原始用量权重，以便余额正确归属。
- `consumption_delta > 0` 表示增加统计消费，对应 `balance_delta = -consumption_delta`；反之亦然。
- 新消费校准的正负差额都进入统计；旧余额校准仍仅将负向余额差额视为消费补差。

## Historical Data

迁移为已有的“同一主记录同时含 Token 与余额差额且已有 Token 日分摊”数据回填每日余额差额，采用同样的百万分之一单位最大余数规则。无法从 Token 日分摊推断日期的 balance-only 旧记录保持 `created_at` 口径。

## Compatibility And Rollback

- API 新增可选 `consumption` 输入和消费审计响应字段；现有 `balance` 输入保持原语义。
- 新列允许空值；旧应用代码可忽略该列，数据库迁移可先于应用发布。
- 回滚应用时旧代码仍按 `created_at` 查询；回滚迁移只需删除新列，但会失去已生成的按日余额归属。

## Rejected Alternatives

- 将整笔余额差额归到开始日或结束日：无法反映跨日 Token 分布。
- 查询时按范围重算比例：每个统计入口重复复杂逻辑，且舍入难以保证分日合计与总账完全一致。
- 新建独立余额分摊表：与现有同一轮校准按日记录重复，增加不必要的表和关联。
