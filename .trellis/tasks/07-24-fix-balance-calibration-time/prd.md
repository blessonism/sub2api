# 修复余额校准时间归属

## Goal

余额校准与同次 Token 校准使用一致的统计归属日期，并支持直接校准所选时间范围的总消费，确保消费统计、钱包余额和总账能够相互核对。

## Background

- Token 校准按管理员选择的开始、结束日期生成按日分摊记录，统计查询按 `allocation_date` 汇总。
- 余额扣减校准当前按审计记录的 `created_at` 汇总，因此历史校准全部计入实际操作当天。
- 余额校准只在 `balance_delta < 0` 时作为消费金额补差；正向余额调整不增加消费金额。
- 审计操作时间仍需保留，不能用统计归属日期覆盖 `created_at`。

## Requirements

- 同一次请求同时包含 Token 和余额校准时，余额消费补差必须落入 Token 校准选择的日期范围，而不是操作当天。
- 跨多日的余额消费补差必须有确定性的按日归属，所有日期之和精确等于本次余额消费补差，不能在多个查询区间重复计入。
- 跨多日时按各日原始 Token 用量占比分摊余额消费补差；最小单位为 `0.000001`，舍入余数按确定性顺序补齐。
- 用户总消费、今日消费、指定时间范围消费、管理员汇总与批量用户统计必须共用同一余额校准归属口径。
- Token 校准现有按日分摊、余额实际更新、负余额保护、审计操作时间和普通用户不可见性保持不变。
- 历史数据兼容策略需明确，不能静默改变无法推断统计归属日期的旧余额校准记录。
- 可由同一记录的 Token 日分摊推断归属的历史余额校准需要回填；没有 Token 日期依据的余额-only 历史记录继续按操作时间统计。
- 新增独立的消费校准，支持对所选日期范围输入消费增减量或目标总消费。
- 消费校准由后端在事务内读取当前范围总消费并计算实际消费差额，不能依赖前端预览值作为账务依据。
- 消费增加时按相同金额扣减用户余额；消费减少时按相同金额退回用户余额。
- 消费校准后所选范围总消费和用户余额均不得小于 0。
- 消费差额按所选范围各日原始 Token 用量占比分摊，逐日消费差额之和等于整笔消费差额。
- 现有余额校准输入与历史数据语义保持不变，消费校准使用独立请求和审计字段。

## Acceptance Criteria

- [x] 管理员在非当天日期范围同时提交 Token 与负向余额校准后，操作当天统计不再包含该余额消费补差。
- [x] 指定 Token 校准日期范围的统计包含对应余额消费补差。
- [x] 跨多日分摊的余额消费补差逐日求和等于本次 `-balance_delta`，不存在重复或遗漏。
- [x] 总消费金额仍包含全部负向余额校准，正向余额校准仍不计入消费金额。
- [x] 单用户、批量用户、今日和任意时间范围查询结果使用相同归属规则。
- [x] 回归测试覆盖历史日期、跨日求和、无时间范围总计和正向余额校准。
- [x] 管理员可将所选范围总消费增加或减少指定金额，并看到钱包余额发生等额反向变化。
- [x] 管理员可把所选范围总消费设置为目标值，后端基于事务内当前值计算差额。
- [x] 消费目标小于 0、消费下调后小于 0 或消费增加导致余额小于 0 时，整笔事务失败。

## Out of Scope

- 不改变余额校准对 `users.balance` 的实时更新方式。
- 不向普通用户展示校准审计记录。
- 不修改 Token 校准的现有分摊算法。
- 不把消费校准伪装成普通请求明细。

## Technical Notes

- 根因位于 `backend/internal/repository/admin_usage_calibration_repo.go`：`SumBalanceSpent`、`SumBalanceSpentByUsers` 和排行榜辅助汇总均按 `admin_usage_calibrations.created_at` 过滤。
- 当前 Token 日分摊表 `admin_usage_calibration_daily_allocations` 只有 `token_delta`，若余额需要逐日精确归属，需在同一张分摊表记录余额日差额或引入等价的单一持久化口径。
- 本任务以 `custom/main` 为 base branch，工作分支使用 `fix/balance-calibration-time`。
