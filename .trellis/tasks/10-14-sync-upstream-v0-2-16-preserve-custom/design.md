# 同步设计

## 分支与固定引用

- 从本地 `custom/main` 的 `b16284c40d5bf8cd99dc5c77ff683ce3c450295a` 创建 `sync/upstream-0.2.16`。
- 预检与实际合并使用同一官方 SHA：`4d9ac3e482106d2da3a39fe3e546d8d6801f1cc1`。
- `git merge --no-commit --no-ff` 保留双方历史，先形成可检查的合并工作区。
- 不在 `custom/main` 试合并；通过下游同步流程把验证后的同步结果合回目标分支。

## 冲突处理原则

逐块比较共同祖先、下游和上游改动。对不相互排斥的二开与上游字段、构造参数、校验、路由和 UI 合并保留；对同一行为的变更按完整数据流检查后适配。

- 分组：保留二开的分时倍率与公开分组账号绑定，同时接入官方分组国际化和平台变更。
- 渠道状态与监控：保留二开接口与配置，适配官方新增的可用渠道、探测和计费契约。
- 网关与计费：保留对话捕捉和本地调度扩展，同时保留官方计费与协议修复。
- Ent：合并 schema 源文件后重新生成，避免手工拼接生成代码。
- Wire：合并 provider 和 cleanup 源文件后重新生成，覆盖二开后台 worker 和官方新增服务。
- 前端：同步 TypeScript DTO、分组编辑和渠道状态视图；保留中文/英文 overlay 的覆盖关系。

## 验证

先用固定引用的预检报告选择定向检查，避免未提交 merge 的 `HEAD` 尚未包含上游导致漏选。冲突处理后的额外风险补充最接近的既有测试。

定向检查通过后，执行项目要求的前端 lint/typecheck/关键测试、后端单元测试及可用的 integration。真实 integration 环境不可用时记为未验证，不替换为 mock。

## 提交与交付边界

项目工作流要求 `git commit`、`git push` 明确确认，并要求同步分支通过目标为 `custom/main` 的 PR 合入。先完成解决冲突与验证，再呈现具体差异、检查结果、提交/推送影响与回滚方式，申请所需确认。若用户明确选择只更新本地，可按该明确指令完成本地合入。

## 回滚

- 未提交合并：`git merge --abort`，同步前的 `custom/main` 不受影响。
- 已提交同步：在同步分支 `git revert -m 1 <merge-commit>`。
- 已合回目标：回退对应 PR/merge commit，不强制重置共享分支。

## 旧失败修复与本地交付

用户已授权修复已有失败并提交本地更新。真实行为问题在生产实现修复；过时测试改为验证当前明确接口契约，mock 保持完整且不依赖网络 DNS 或全局堆内存噪声。验收通过后直接提交并快进 `custom/main`，无需再次确认，不推送。
