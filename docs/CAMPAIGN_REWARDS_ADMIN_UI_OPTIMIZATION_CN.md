# 邀请活动管理员侧 UI 优化方案

> 视图：`frontend/src/views/admin/CampaignRewardsView.vue`
> 路由：`/admin/activities`（`AdminActivities`，`/admin/campaign-rewards` 为向后兼容的旧入口）
> 接口：`frontend/src/api/admin/campaigns.ts`
> 记录日期：2026-07-04
> 对应 Trellis 任务：`.trellis/tasks/07-04-ui`

---

## 1. 背景与目标

邀请活动管理员页当前已经具备活动列表、活动详情、奖池概览、奖池调整、配置版本、榜单、预览结算、最终结算和发放等基础能力。页面适合作为第一版运营后台，但在活动生命周期表达、资金类动作防误触、规则配置可解释性和结算结果审阅上仍有优化空间。

本方案目标不是重做页面，而是在现有组件和 API 基础上提高管理员的判断效率与操作安全：

- 让管理员一眼看懂活动当前处于哪个阶段，以及下一步应该做什么。
- 降低发布、冻结、最终结算、奖励发放等高风险动作误触概率。
- 把创建活动从“默认草稿”升级为可审阅、可调整的配置流程。
- 强化奖池、规则版本、结算预览和榜单之间的解释关系。
- 尽量复用现有页面结构、接口字段和通用组件，避免引入大范围重构。

---

## 2. 当前页面速览

现有管理员页主要结构如下：

```
AppLayout
├── 顶部操作区：刷新、创建默认活动
├── 左侧活动列表：名称、时间、状态
└── 右侧详情区
    ├── 活动标题、描述、时间、操作按钮
    ├── 奖池指标卡：确认奖池、待确认奖池、调整奖池、最终奖池
    ├── 奖池调整表单
    ├── 配置版本表单
    ├── 结算汇总卡
    └── 榜单表
```

对应 API 已支持的关键能力：

- 活动创建：基础信息、封面、规则文本、预热/活动/审核/公示/发放时间、初始奖金、充值门槛、注入比例、排名池比例、贡献池比例、排名权重、最低发放金额。
- 活动流转：发布、冻结榜单、重新计算奖励、最终计算、发放。
- 奖池运营：查询奖池汇总、手动调整奖池。
- 数据审阅：排行榜、计算汇总、奖励结果明细。

## 3. 核心问题

### 3.1 生命周期顺序不够清晰

当前右侧操作按钮平铺展示：发布、冻结、预览、结算、发放。管理员能看到动作，但不容易判断推荐顺序、当前阶段、哪些动作还不该执行。

影响：

- 容易把“预览”和“最终结算”混淆。
- 冻结、结算、发放之间缺少阶段解释。
- 只有发布按钮根据 `draft` 禁用，其他动作缺少状态级约束。

### 3.2 资金类动作缺少确认上下文

最终结算和奖励发放会影响真实余额或奖励批次，但当前动作只依赖按钮点击和 Toast 反馈。

影响：

- 发放前缺少本次发放金额、人数、扣留金额、批次号确认。
- 误触风险高，且管理员无法在确认前快速复核计算结果。
- 失败时只能看到通用错误，缺少“是否已发放、是否重复发放”的业务解释入口。

### 3.3 创建活动过于黑盒

`createDraft` 当前直接创建默认活动，默认时间、门槛、比例、权重都写在前端函数中。

影响：

- 管理员无法在创建前确认规则。
- 默认值不可见，运营同学需要创建后再理解草稿内容。
- API 已有丰富字段，但 UI 未充分暴露。

### 3.4 奖池调整缺少影响预览

当前奖池调整表单只有类型、金额、原因和提交按钮。

影响：

- 管理员不知道提交后最终奖池如何变化。
- 扣减和追加的视觉语义不够明显。
- 原因字段可空，不利于后续审计。

### 3.5 规则版本变更缺少“当前版本基线”

配置版本区只暴露充值门槛、注入比例、原因，没有展示当前规则摘要。

影响：

- 管理员不知道自己是在基于哪一版规则修改。
- 排名池比例、贡献池比例、排名权重、最低发放金额等关键规则在 UI 上不可见。
- 后续排查奖励计算时不易追溯。

### 3.6 结算结果明细未展示

接口 `CampaignCalculationSummary` 已返回 `results`，但页面目前只展示四个汇总指标。

影响：

- 管理员不能在页面上审阅单个用户奖励拆分。
- 低于最低发放、扣留原因、舍入残差等重要信息不可见。
- 发放前无法完成足够充分的人工复核。

## 4. 设计原则

- **以流程为主线**：活动管理页先回答“现在在哪一步”，再回答“可以做什么”。
- **资金动作必须可复核**：最终结算和发放前展示金额、人数、扣留、批次等确认信息。
- **保持后台工具感**：页面以扫表、复核、下钻为主，不做偏营销化视觉。
- **复用现有能力**：优先复用 `BaseDialog`、`ConfirmDialog`、`EmptyState`、`LoadingSpinner`、`Icon`、`appStore.showSuccess/showError` 等现有模式。
- **接口先不扩张**：第一阶段尽量基于现有 `campaignsAdminAPI` 返回字段完成，后续再考虑补充审计日志、历史版本列表等接口。

## 5. 优化方案

### 5.1 活动生命周期流程条

在活动详情卡顶部加入阶段流程条，替代当前“按钮平铺但无顺序”的主要认知入口。

推荐阶段：

```
草稿 → 预热/待开始 → 进行中 → 已冻结 → 已结算 → 已发放
```

展示内容：

- 当前阶段高亮。
- 已完成阶段显示完成态。
- 下一步阶段展示推荐动作按钮。
- 不可执行阶段展示原因，例如“请先冻结榜单后再最终结算”。

首版可按 `selectedCampaign.status` 和本地 `calculation` 状态派生，不强依赖后端新增字段。

### 5.2 高风险动作确认弹窗

将以下动作接入确认弹窗：

- 冻结榜单。
- 最终结算。
- 奖励发放。
- 异常扣减类型的奖池调整。

发放确认弹窗建议展示：

- 活动名称和状态。
- 最终奖池。
- 本次最终发放金额。
- 扣留金额。
- 发放用户数。
- 计算批次号。
- 确认文案：“确认后将执行奖励发放，请确认已完成结算结果复核。”

如果页面还没有最终计算结果，点击“发放”时应引导先执行最终结算，而不是直接调用发放接口。

### 5.3 创建活动向导

将“创建默认活动”改成“创建活动”弹窗向导，默认值沿用现有 `createDraft`，但允许管理员创建前确认。

建议分三步：

1. **基础信息**
   - 活动名称、描述、规则文本、封面 URL。
   - 活动开始和结束时间。
   - 可选展示预热、审核、公示、发放截止时间。

2. **奖励规则**
   - 初始奖金。
   - 充值达标门槛。
   - 是否累计充值。
   - 奖池注入比例。
   - 排名池比例和贡献池比例。
   - 排名奖励人数和权重。
   - 最低发放金额。

3. **确认创建**
   - 展示规则摘要。
   - 展示时间线。
   - 展示默认权重是否合计合理。
   - 提交后创建草稿并自动选中新活动。

### 5.4 左侧活动列表增强

现有列表保留，但增加快速筛选和关键信息。

建议：

- 顶部增加状态筛选：全部、草稿、进行中、已冻结、已发放。
- 活动卡增加最终奖池或有效邀请数摘要。
- 对即将结束、待发放、待结算活动加轻量提醒。
- 当前选中态保持现有 `primary` 背景。

首版如果列表接口没有奖池摘要，可以只做状态筛选和时间提醒，不阻塞整体方案。

### 5.5 奖池调整影响预览

奖池调整表单下方增加实时影响预览：

```
当前最终奖池：¥10,000.00
本次调整：+¥500.00
调整后预计：¥10,500.00
```

交互规则：

- 追加奖励和人工补偿用绿色正向语义。
- 异常扣减用红色负向语义。
- 原因字段建议必填。
- 异常扣减提交前二次确认。

### 5.6 规则版本摘要卡

在“配置版本”表单上方增加当前规则摘要卡。

建议展示：

- 充值门槛。
- 奖池注入比例。
- 排名池比例 / 贡献池比例。
- 排名奖励人数。
- 最低发放金额。
- 排名权重摘要，例如 `30 / 20 / 15 / ...`。

配置变更提交后建议刷新活动详情或提示“新版本已创建，请刷新后查看当前版本”。

### 5.7 结算预览结果明细

当 `calculation` 存在时，在汇总卡下方增加结果明细表或抽屉。

建议列：

- 用户。
- 排名。
- 排名奖励。
- 贡献奖励。
- 毛奖励。
- 最终发放。
- 扣留金额。
- 扣留原因。
- 舍入残差。

展示策略：

- 默认只展示前 20 条，提供“查看全部”或滚动表。
- `withheld_amount_cents > 0` 的行用 amber 标记。
- `final_payout_amount_cents = 0` 且有扣留原因时突出展示。
- 发放确认弹窗应引用同一份计算结果。

### 5.8 榜单表增强

现有榜单表保留基础列，补充用于运营判断的信息。

建议：

- Top 3 排名轻量突出，但不要过度装饰。
- 增加奖励拆分入口，点击行可查看预计奖励构成。
- 增加“是否可能低于最低发放”提示。
- 用户列可复用现有用户名、脱敏邮箱、用户 ID 兜底逻辑。

## 6. 建议实施阶段

### R1：安全与流程优先

首轮优先做低接口依赖、高收益改造：

- 活动生命周期流程条。
- 冻结、最终结算、发放确认弹窗。
- 发放前缺少最终计算结果时的引导。
- 奖池调整影响预览和异常扣减确认。

收益：

- 明显降低误操作风险。
- 管理员能按流程完成活动闭环。
- 改动主要集中在 `CampaignRewardsView.vue`。

### R2：创建与规则配置体验

第二轮优化活动配置入口：

- 创建活动向导。
- 当前规则摘要卡。
- 版本变更表单说明和提交后刷新。
- 排名权重校验提示。

收益：

- 默认规则透明化。
- 降低创建后再返工的概率。
- 为后续支持多活动模板打基础。

### R3：审阅与数据下钻

第三轮强化结算复核能力：

- 结算结果明细表或抽屉。
- 扣留、最低发放、舍入残差提示。
- 榜单行详情。
- 左侧活动列表筛选和待处理提醒。

收益：

- 发放前审阅链路更完整。
- 运营和财务排查更方便。
- 可逐步承接更多后端审计字段。

## 8. 验收标准

R1 验收：

- [ ] 活动详情顶部能展示生命周期阶段和下一步推荐动作。
- [ ] 冻结、最终结算、发放都有确认弹窗。
- [ ] 发放确认能展示最终发放金额、扣留金额、用户数和批次号。
- [ ] 没有最终计算结果时，不能直接发放，并提示先执行最终结算。
- [ ] 奖池调整能展示调整前、调整金额、调整后预计奖池。
- [ ] 异常扣减需要二次确认，原因字段不能为空。

R2 验收：

- [ ] 创建活动不再直接静默创建默认草稿，而是进入可确认的创建弹窗或向导。
- [ ] 默认规则值仍与当前 `createDraft` 保持一致。
- [ ] 创建前能看到时间线、充值门槛、注入比例、奖池拆分、排名权重和最低发放金额。
- [ ] 配置版本区域能展示当前规则摘要。
- [ ] 排名权重明显异常时有前端提示。

R3 验收：

- [ ] 预览或最终结算后能查看奖励结果明细。
- [ ] 扣留金额、扣留原因、舍入残差可见。
- [ ] 榜单表能辅助判断 Top 用户、低于最低发放和奖励构成。
- [ ] 活动列表支持按状态筛选。

## 9. 暂不纳入范围

- 不新增后端接口，除非实现过程中发现现有返回字段无法支撑基础确认。
- 不做完整活动模板系统。
- 不重构用户侧活动页。
- 不改变奖励计算逻辑。
- 不改变活动结算和发放的后端幂等策略。
- 不引入新的 UI 组件库。

---

## 10. 风险与注意事项

- **状态派生风险**：如果后端 `status` 不能完整表达结算状态，前端流程条只能作为弱提示。后续可补充批次状态或最终计算状态字段。
- **发放重复风险**：UI 确认只能降低误触，不能替代后端幂等保护；后端已存在的幂等与已发放校验仍是最终防线。
- **表单复杂度风险**：创建向导字段较多，首版应保持默认值和折叠高级项，避免运营创建成本过高。
- **结果明细性能风险**：`calculation.results` 可能较大，首版限制展示条数或使用抽屉分页更稳妥。

---

## 11. 推荐优先级

建议优先交付 R1：

1. **生命周期流程条**：解决“现在在哪一步”的核心认知问题。
2. **高风险确认弹窗**：保护冻结、最终结算和发放动作。
3. **奖池调整影响预览**：让资金调整更可解释。

R1 不需要扩接口，主要是前端交互和信息架构调整，最适合作为下一轮小步快跑。
