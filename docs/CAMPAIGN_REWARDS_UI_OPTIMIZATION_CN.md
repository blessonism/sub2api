# 邀请活动 UI 设计优化方案

> 用户侧视图：`frontend/src/views/user/CampaignRewardsView.vue`
> 管理员侧视图：`frontend/src/views/admin/CampaignRewardsView.vue`
> 用户侧主路由：`/activities`（`/campaign-rewards` 为向后兼容的旧入口）
> 管理员侧路由：`/admin/activities`（`/admin/campaign-rewards` 为向后兼容的旧入口）
> 最后更新：2026-07-04
> Trellis 任务：`.trellis/tasks/07-04-ui`

---

## 1. 设计目标

邀请活动页面的核心目标不是单纯展示活动规则，而是让用户和管理员都能快速回答各自最关心的问题。

用户侧需要回答：

- 当前有没有活动？
- 活动什么时候开始/结束？
- 我现在应该做什么？
- 我的邀请是否有效？
- 我预计能拿多少奖励？
- 最终结算以什么为准？

管理员侧需要回答：

- 活动处在哪个阶段？
- 时间线是否配置正确？
- 用户侧当前会看到什么？
- 奖金池、榜单和结算结果是否可信？
- 哪些操作是高风险、不可轻易重复执行？

本方案的优化重点是：

1. 用生命周期倒计时强化活动节奏。
2. 用更清晰的信息架构提升用户转化。
3. 用运营控制台降低管理员误操作和理解成本。
4. 复用当前已有字段和接口，避免脱离现有结算链路重做。

## 4. 生命周期倒计时设计

### 4.1 推荐原则

倒计时由活动生命周期字段驱动：

- 管理员配置活动时间线。
- 前端根据 `campaign.status` 和时间字段计算当前倒计时目标。
- 用户侧与管理员侧预览共用同一套展示规则。
- 不新增独立的 `countdown_end_at`，避免与活动真实结束时间冲突。

### 4.2 用户侧倒计时规则

| 活动状态 | 倒计时目标 | 用户侧标题 | 主行动 |
|---|---|---|---|
| `draft` | 无 | 活动准备中 | 不展示用户参与入口 |
| `warmup` | `start_at` | 距活动开始 | 可提前复制邀请链接、查看规则 |
| `active` | `end_at` | 距活动结束 | 强化复制邀请链接 |
| `auditing` | `audit_end_at` | 审核预计剩余 | 不再催促邀请，强调结果审核中 |
| `publicizing` | `publicity_end_at` | 公示剩余 | 引导查看榜单和邀请记录 |
| `pending_payout` | `payout_due_at` | 距最晚发放 | 强调奖励待发放 |
| `paid` | 无 | 奖励已发放 | 展示最终结果 |
| `cancelled` | 无 | 活动已取消 | 展示取消说明 |
| `terminated` | 无 | 活动已提前终止 | 展示终止说明 |

当目标时间为空或已过期：

- 不显示负数倒计时。
- 降级为阶段说明，例如“审核时间待确认”“活动已结束，等待结算”。
- 前端不可自行推进状态，只展示后端返回状态。

### 4.3 倒计时显示格式

推荐格式：

- 大于 24 小时：`2 天 03:12:08`
- 小于 24 小时：`03:12:08`
- 小于 1 分钟：`即将开始` 或 `即将结束`

移动端：

- 保留标题与最大两个时间单位，例如 `2 天 3 小时`。
- 秒级变化可保留在桌面端，移动端可降低视觉占比，避免布局跳动。

### 4.4 组件建议

建议新增一个轻量组件或组合式函数：

- `CampaignCountdown.vue`
- 或 `useCampaignLifecycleCountdown.ts`

输入：

- `campaign`
- 当前时间，可默认内部定时刷新

输出：

- `phaseLabel`
- `targetAt`
- `remainingText`
- `variant`
- `isUrgent`
- `isActionable`

这样用户页和管理员页预览可以复用同一套规则。

## 5. 用户侧 UI 优化

### 5.1 Hero 区重构

当前 Hero 已展示活动状态、名称、说明、起止时间和预计奖金池。建议改为“状态 + 倒计时 + 行动”的结构：

- 左侧：状态 badge、活动名、活动说明、规则摘要。
- 中间或右侧：生命周期倒计时卡片。
- 右侧底部：主按钮“复制邀请链接”。
- 奖金池从唯一视觉焦点降级为辅助指标，避免用户只看金额却不知道下一步。

推荐文案：

- 预热中：`活动即将开始，先准备好你的邀请链接`
- 进行中：`邀请有效用户达标后即可参与奖励分配`
- 审核中：`邀请数据正在审核，最终奖励以结算结果为准`
- 公示中：`榜单正在公示，异常记录可能调整`
- 待发放：`奖励已结算，等待发放`

### 5.2 我的进度概览

当前 4 张指标卡可以保留，但建议增加层级：

- 第一优先级：预计奖励、有效邀请、当前排名。
- 第二优先级：待审核邀请。

当 `current_rank` 为空时，不只显示“未上榜”，建议补一句：

- `再获得 1 个有效邀请后有机会进入榜单`
- 如果后端已有 `distance_to_top10`，优先展示 `距离 Top10 还差 N 个有效邀请`。

### 5.3 邀请入口强化

当前邀请码和邀请链接分列展示，建议优化为：

- 邀请链接作为主入口，按钮更醒目。
- 邀请码作为备用入口。
- 复制成功后 toast 保留。
- 可选增强：后续增加二维码，不纳入第一阶段必做。

推荐布局：

```text
我的邀请链接
[ https://.../invite/ABC123               ][复制链接]

邀请码
[ ABC123                                  ][复制邀请码]
```

### 5.4 奖励进度表达

当前奖励拆分已有三张小卡。建议补一块“进度解释”：

- `预计排名奖励`
- `预计贡献奖励`
- `有效充值贡献`
- `距离上一名还差 N 个有效邀请`
- `距离 Top10 还差 N 个有效邀请`

注意：

- `distance_to_previous` 和 `distance_to_top10` 为 0 或空时，不要误导为已经达成，应结合 `current_rank` 判断文案。
- 奖励为预估时必须持续展示“最终以审核结算为准”。

### 5.5 活动规则从固定文案升级为摘要 + 完整规则

当前规则卡片使用固定 i18n 文案。建议：

- 默认展示 3 条规则摘要。
- 完整规则优先展示后端 `rules_text`。
- `rules_text` 为空时再使用 i18n 默认规则。
- 完整规则使用折叠面板，避免首屏过长。

规则摘要建议：

- 什么样的邀请算有效。
- 奖金池如何生成。
- 奖励如何分配。
- 什么时候结算和发放。

### 5.6 排行榜优化

当前排行榜已经具备核心列。建议增强：

- 高亮当前用户所在行。
- 如果当前用户未进入前 50，表格下方显示“我的排名摘要”。
- 排名列 Top3 使用轻量视觉强调，但不要过度动画。
- 保留邮箱/用户名脱敏展示，避免隐私压力。

### 5.7 邀请记录优化

当前邀请记录表已经展示状态和时间。建议增强状态解释：

- `registered`：已注册，等待充值达标。
- `recharge_unqualified`：充值未达到有效门槛。
- `pending_audit`：已达标，等待审核。
- `effective`：已生效，计入奖励。
- `invalid`：已失效，不计入奖励。
- `risk_review`：风控审核中。

建议在状态 badge hover 或移动端详情中展示原因：

- `invalid_reason`
- `audit_note`
- `risk_level`

第一阶段可以先在表格中补“说明”列；如果移动端空间不足，用行内展开。

### 5.8 空状态

无活动：

- 标题：`当前没有进行中的邀请活动`
- 描述：保留现有文案。
- 如果后台有预热活动但用户接口未返回，需要后续确认 `GetActiveHome` 是否应返回 warmup 活动。

无邀请记录：

- 不只显示“暂无邀请记录”。
- 增加主按钮：`复制邀请链接`。
- 文案：`把链接发给好友，好友注册并完成有效充值后会显示在这里。`

## 6. 管理员侧 UI 优化

### 6.1 活动列表

当前左侧列表展示名称、起止时间、状态。建议补充：

- 当前阶段倒计时，例如 `距结束 2 天`。
- 风险提示，例如活动时间配置不完整时显示 amber badge。
- 活动状态分组或筛选：全部、草稿、进行中、待结算、已结束。

第一阶段可以只增加倒计时和异常提示，不急着做筛选。

### 6.2 活动详情头部

当前详情头部按钮较多，建议按风险和阶段分组：

- 常规：编辑/刷新/预览用户侧。
- 发布：发布活动。
- 结算：冻结榜单、预览结算、最终结算。
- 发放：一键发放。

高风险动作必须有二次确认：

- 发布活动。
- 冻结榜单。
- 最终结算。
- 一键发放。
- 人工调减奖金池。

确认弹窗应展示影响范围和不可逆程度。

### 6.3 生命周期时间线配置

管理员需要一个明确的“活动时间线”模块，而不是只在创建默认活动时隐式生成时间。

字段建议：

- 预热开始时间：`warmup_start_at`
- 活动开始时间：`start_at`
- 活动结束时间：`end_at`
- 审核开始时间：`audit_start_at`
- 审核结束时间：`audit_end_at`
- 公示开始时间：`publicity_start_at`
- 公示结束时间：`publicity_end_at`
- 最晚发放时间：`payout_due_at`

交互建议：

- 使用纵向时间线展示阶段。
- 每个阶段显示开始/结束时间和对应用户侧文案。
- 缺失必要字段时提示“该阶段倒计时不可用”。
- 保存前做前端校验，后端也必须做最终校验。

推荐时间顺序：

```text
warmup_start_at <= start_at < end_at <= audit_start_at <= audit_end_at <= publicity_start_at <= publicity_end_at <= payout_due_at
```

允许部分阶段为空，但如果状态会进入对应阶段，目标时间应完整。

### 6.4 用户侧预览

管理员调整时间线后，应该能直接看到用户侧关键展示：

- 当前用户侧阶段标题。
- 倒计时目标和剩余时间。
- 活动说明。
- 主行动按钮是否可用。
- 规则摘要。

预览不需要完全复制用户页面，只需展示 Hero 区和关键状态即可。

### 6.5 奖金池与配置版本

当前奖金池与配置版本表单可以保留，但建议增强解释：

- `已确认奖金池`：已达标并确认计入的奖金池金额。
- `待确认奖金池`：充值或邀请仍待确认的金额。
- `调整金额`：管理员手动追加、补偿或调减。
- `最终奖金池`：结算时用于分配的金额。

配置版本建议显示当前版本信息：

- 生效时间。
- 有效充值门槛。
- 注入比例。
- 是否允许累计充值。
- 变更原因。

如果当前接口没有返回版本列表，可先在文档中作为后续增强，不阻塞第一阶段 UI。

### 6.6 结算与发放结果

当前结算摘要只显示四个金额。建议补充：

- 本次计算状态：预览/最终。
- 计算批次号。
- 涉及用户数。
- 最低发放门槛回收金额。
- 四舍五入残差。
- 发放批次状态：处理中、部分成功、成功、失败。

如果接口已返回 `CampaignCalculationSummary.results`，管理员侧可以增加“结算明细弹窗”，第一阶段可先不展开到主表。

### 6.7 管理员邀请明细入口

用户侧已有邀请记录，管理员侧目前只展示排行榜。建议后续补一个邀请明细入口：

- 按活动查看全部邀请记录。
- 支持状态筛选：待审核、有效、无效、风控审核中。
- 展示邀请人、被邀请人、注册时间、达标时间、有效充值、风控等级、审核状态。

这部分更偏运营审核，建议作为第二阶段。

### 7.1 前端可直接复用

- `campaign`

用户侧现有 `CampaignMyData` 已包含：

- `pending_invite_count`
- `invalid_invite_count`
- `current_rank`

- `estimated_total_reward_cents`

- `distance_to_previous`

管理员侧创建接口已支持时间字段：

- `warmup_start_at`

- `audit_end_at`
- `publicity_start_at`
- `publicity_end_at`

### 7.2 可能需要补充

后续实现时需要确认管理员侧是否已有“更新活动基础信息/时间线”的 API。如果没有，建议补：

- `PATCH /admin/campaigns/:id`
- 支持更新名称、描述、封面、规则、生命周期时间。
- 只允许草稿/预热阶段改关键时间；活动进行中修改必须记录版本或操作日志。

如果希望减少前端重复计算，可由后端补充只读派生字段：

- `current_phase`
- `countdown_target_at`
- `countdown_label`
- `is_actionable`

但第一阶段更推荐前端先基于现有字段计算，避免接口扩散。

### 7.3 时间与时区

- 后端继续使用 ISO 时间字符串。
- 前端展示使用本地时区格式化。
- 倒计时计算使用 `Date` 时间戳差值。
- 文案不展示服务器时区，避免普通用户困惑。
- 管理员时间选择器应明确显示本地时间。

## 8. 推荐实施拆分

### R1：生命周期倒计时与用户侧 Hero

目标：

- 新增倒计时计算工具或组件。
- 用户侧 Hero 展示状态、倒计时、主行动按钮。
- 活动期/预热期/审核期/公示期/待发放状态文案完整。

验收：

- 不同 `status` 和时间组合下显示正确阶段文案。
- 不出现负数倒计时。
- 活动结束后不再突出邀请 CTA。

### R2：用户侧进度、规则和记录可信度

目标：

- 强化我的进度与距离提示。
- 规则改成摘要 + 完整规则折叠。
- 邀请记录补充状态解释或说明列。
- 空状态加入复制链接引导。

验收：

- 用户能清楚知道“为什么这条邀请未生效”。
- 预估奖励和最终结算的边界持续可见。
- 移动端表格不挤压核心信息。

### R3：管理员时间线与用户侧预览

目标：

- 管理员页新增生命周期时间线模块。
- 新增用户侧预览卡。
- 补齐时间顺序校验。

验收：

- 管理员调整时间后能看到用户侧倒计时文案。
- 时间不合法时无法保存，并给出明确提示。
- 缺失可选阶段时间时有降级说明。

### R4：管理员操作安全与结算解释

目标：

- 高风险动作接确认弹窗。
- 结算摘要补充批次、状态、用户数和回收原因。
- 一键发放结果明确展示成功/失败状态。

验收：

- 发布、冻结、最终结算、发放前都有二次确认。
- 管理员能理解金额从奖金池到最终发放的变化。
- 发放失败不会被误认为成功。

### R5：管理员邀请审核明细

目标：

- 增加活动邀请明细入口。
- 支持按状态筛选和查看风险/审核原因。

验收：

- 管理员可定位异常邀请记录。
- 用户侧“待审核/无效”状态可以被后台解释。

## 10. 边界与风险

### 10.1 状态与时间不一致

风险：

- 状态是 `active`，但 `end_at` 已过。
- 状态是 `auditing`，但 `audit_end_at` 为空。

处理：

- 前端只展示后端状态，不自行修改状态。
- 倒计时目标缺失时展示阶段说明。
- 管理员侧给出时间线异常提示。

### 10.2 预估奖励误解

风险：

- 用户把预计奖励理解为已到账。

处理：

- 预计金额附近始终显示 `最终以审核结算为准`。
- 审核/公示/待发放阶段调整 CTA 文案。

### 10.3 高风险操作误触

风险：

- 管理员误点最终结算或一键发放。

处理：

- 所有高风险动作接确认弹窗。
- 确认弹窗说明影响范围。
- 发放结果必须展示批次状态。

### 10.4 移动端表格可读性

风险：

- 排行榜和邀请记录列多，移动端横向滚动体验差。

处理：

- 第一阶段保留横向滚动。
- 第二阶段可考虑移动端卡片化邀请记录。

## 11. 验收标准

### 用户侧

- [ ] 活动 Hero 能按状态展示正确倒计时和阶段文案。
- [ ] 邀请链接复制入口在活动期足够明显。
- [ ] 预热、活动中、审核、公示、待发放、已发放状态均有合理文案。
- [ ] 我的进度能展示排名、有效邀请、预计奖励和差距提示。
- [ ] 规则区域支持摘要与完整规则。
- [ ] 邀请记录状态可解释，不只显示内部状态值。
- [ ] 无活动和无邀请记录均有明确下一步引导。

### 管理员侧

- [ ] 活动列表能显示状态和当前阶段倒计时。
- [ ] 活动详情有生命周期时间线。
- [ ] 管理员能预览用户侧当前看到的阶段文案。
- [ ] 时间配置保存前有顺序校验。
- [ ] 发布、冻结、最终结算、一键发放有确认弹窗。
- [ ] 结算摘要能解释最终发放、回收金额和批次状态。

### 技术与质量

- [ ] 倒计时规则在用户侧和管理员侧复用，不复制两套判断。
- [ ] i18n 文案中英文均补齐。
- [ ] 不引入独立倒计时字段与生命周期字段冲突。
- [ ] 不破坏现有活动创建、发布、结算和发放接口。
- [ ] 前端单元测试覆盖核心倒计时状态。

## 12. 推荐优先级

第一优先级：

- 生命周期倒计时。
- 用户侧 Hero 重构。
- 管理员用户侧预览。
- 高风险操作确认。

第二优先级：

- 规则折叠与 `rules_text` 展示。
- 邀请记录状态解释。
- 奖励差距提示。
- 时间线编辑体验。

第三优先级：

- 二维码/分享海报。
- 移动端邀请记录卡片化。
- 管理员邀请审核明细。
- 排行榜高级筛选。

---

## 13. 结论

邀请活动 UI 的关键优化方向是把页面从“数据展示页”升级为“活动参与与运营控制台”。

倒计时应作为活动生命周期的表达层，而不是独立业务模型。用户侧用它强化行动节奏，管理员侧用它校验配置和预览效果。这样既能提升邀请转化，也能保持当前结算、排行榜和发放链路的稳定性。
