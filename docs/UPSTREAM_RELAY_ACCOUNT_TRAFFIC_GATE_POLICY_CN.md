# 上游账号流量闸门自动策略设计

> 面向功能：上游倍率监控、候选映射、自动推荐、自动应用
> 目标读者：负责 Sub2API 上游账号运营和二开实现的管理员 / 开发者
> 最后更新：2026-06-30

---

## 1. 背景

当前上游倍率监控已经能采集这些信息：

- 上游连接器登录状态、账号余额、最近同步时间；
- 上游分组倍率快照，包括直读倍率和 `/v1/usage` 推导倍率；
- 候选映射，包括本地项目账号、上游分组、上游 API Key、当前 priority；
- 本地账号调度状态，即 `accounts.schedulable`；
- 最近探测结果、健康窗口、连续成功 / 失败、延迟；
- 今日上游分组用量和历史日用量；
- 自动推荐记录和手动 / 自动应用记录。

现有自动推荐主要解决“谁更便宜、更健康，应该排在前面”的问题。它会生成 priority 调整建议，再由管理员或自动策略应用。

但真实运营里，priority 只是排序偏好，不是硬性开关。如果低倍率账号不可用、额度不足、探测失败或被关闭，请求仍可能回落到高倍率账号。这样会出现一个问题：系统看起来已经把便宜账号排前面，但实际流量仍可能打到高成本账号。

本仓当前真实请求调度看的是 `accounts.schedulable` 等账号调度字段，而不是 `upstream_relay_candidates.enabled`。因此第一版流量闸门必须落到账号调度状态：暂停账号承接时写 `accounts.schedulable=false`，恢复账号承接时写 `accounts.schedulable=true`。候选 `enabled` 仍保留为“这个上游分组映射是否纳入监控和推荐输入”的开关，不把它描述成真实流量阻断字段。

因此，自动策略需要从“只调 priority”升级为“控制账号是否承接流量”。

---

## 2. 核心问题

### 2.1 priority 不能表达“禁止使用”

priority 适合表达：

- 低倍率账号优先；
- 健康账号优先；
- 某个上游组临时排后。

priority 不适合表达：

- 这个账号余额不足，不要再承接新流量；
- 这个账号倍率太高，只作为人工兜底，不进入自动路由；
- 这个账号数据过期，暂时不要让自动策略使用；
- 这个上游组连续失败，应先暂停相关账号承接，而不是继续排队等待 fallback。

如果只调 priority，高倍率账号仍然可能在 fallback 链路里被打到。

### 2.2 自动策略的主要风险不是“不够省钱”

更大的风险是：

- 把流量集中到余额不足的账号；
- 因为短期倍率低，把不稳定账号打开；
- 关闭过多候选，导致某个项目账号没有可用上游候选；
- 自动恢复过快，刚恢复的账号又被瞬间打满；
- 管理员只看到结果，看不到为什么关闭或开启。

所以这个功能的第一目标不是追求极致成本最优，而是让自动控制更稳、更可解释、更容易人工接管。

---

## 3. 设计目标

本功能命名为 **上游账号流量闸门**。

这里的“账号”指后台候选映射里的本地项目账号。管理员实际关心的是：某个项目账号是否应该继续承接自动调度流量，以及这个判断来自哪些上游连接器 / 上游分组的健康与倍率信号。

它要解决三个问题：

1. **明确阻断**：当某个账号不应该承接流量时，不只降低 priority，而是建议暂停 `accounts.schedulable`。
2. **谨慎恢复**：当由闸门暂停的账号恢复健康时，先生成恢复建议，避免一恢复就承接大量流量。
3. **可解释可回滚**：每次关闭、开启、跳过自动应用，都记录触发原因、关键指标和恢复条件。

---

## 4. 范围边界

### 4.1 本阶段优先做

本阶段优先落地 **账号级流量闸门 v1**：推荐系统继续基于候选映射收集倍率、探测和健康信号，但真正应用时只修改 `accounts.schedulable`。

第一版采用“建议 + 管理员手动应用”：

- 推荐 run 可以同时包含 `priority_update`、`account_pause`、`account_resume` 三类建议；
- `priority_update` 继续写 `accounts.priority`；
- `account_pause` 写 `accounts.schedulable=false`；
- `account_resume` 写 `accounts.schedulable=true`；
- 暂停来源、原因、来源 run 和 suggestion 写入 `upstream_relay_account_gate_states`；
- 恢复只允许恢复仍有 active gate state 的账号，避免误恢复管理员手动关闭的账号。

这样做的原因：

- 真实调度路径已经读取账号调度字段，落到 `accounts.schedulable` 才能真正阻断流量；
- 候选映射仍然提供必要的监控信号，但候选 `enabled` 不是请求调度闸门；
- 管理员看到的是账号级暂停 / 恢复，和实际影响范围一致；
- v1 不做无人值守自动关停，降低误伤风险。

### 4.2 本阶段不优先做

暂不做复杂的全局规则引擎。

暂不做自动应用账号暂停 / 恢复建议。

暂不做多维权重编辑器。

暂不做完全无人值守的自动恢复。

暂不把连接器 `paused` 作为自动策略的默认动作。连接器级暂停影响面太大，更适合作为人工运维动作，或后续在明确极端条件下支持。

暂不把候选 `enabled` 当作真实流量阻断字段。它仍然只表达候选映射是否启用、是否参与监控和推荐输入。

## 5. 业务动作模型

自动策略不再只有“推荐 priority”，而是分成三类动作。

### 5.1 调整 priority

适用场景：

- 候选健康稳定；
- 倍率更低；
- 数据新鲜；
- 调整后不会明显扩大风险。

动作结果：

- 生成 priority 调整建议；
- 低风险时允许自动应用；
- 高风险时只推荐，不自动应用。

### 5.2 暂停账号承接

适用场景：

- 最近探测失败；
- 健康窗口内连续失败；
- 成功率低于策略阈值；
- 倍率缺失或过期；
- 探测数据过期；
- 倍率来源不可靠，且没有足够健康样本支撑。

动作结果：

- 生成 `account_pause` 建议；
- 管理员确认后写 `accounts.schedulable=false`；
- 写入 gate state，记录暂停来源和原因；
- 写 scheduler outbox，让调度器及时感知账号状态变化；
- 如果这是同平台最后一个 active + schedulable 账号，不生成暂停建议，只保留排除原因。

### 5.3 恢复账号承接

适用场景：

- 账号此前由本功能暂停，且 gate state 仍 active；
- 候选恢复健康；
- 最新探测在新鲜度窗口内；
- 最新倍率在新鲜度窗口内；
- 不再命中推荐排除原因。

动作结果：

- 生成 `account_resume` 建议；
- 管理员确认后写 `accounts.schedulable=true`；
- 标记 gate state 已恢复，记录恢复人和恢复时间；
- 不恢复没有 gate state 的人工关闭账号。

### 5.4 候选映射开关

适用场景：

- 某个候选映射配置错误；
- 某个上游分组不再需要监控；
- 管理员希望临时排除某个候选，不让它参与倍率监控和推荐。

动作结果：

- 修改 `upstream_relay_candidates.enabled`；
- 该候选不再进入监控 / 推荐候选集；
- 不把它作为请求调度层面的账号流量阻断字段。

### 5.5 暂不实现的候选级自动关闭

以下信号仍然重要，但 v1 不自动把它们落到候选 `enabled=false`：

- 倍率高于可接受阈值；
- 连接器余额过低或余额数据过期；
- 今日成本异常增长；
- 候选对应上游组长时间没有新鲜快照。

这些可以进入后续版本的候选级策略，但需要先确认真实调度是否读取候选维度，否则容易出现“界面显示关闭，实际仍被调度”的错觉。

## 6. 最小可用规则

第一版规则要简单、稳、能解释。

### 6.1 暂停账号建议

候选满足以下任一条件时，可以转成“暂停账号承接”建议：

- 最近一次探测失败；
- 连续失败次数大于 0，且策略开启“连续失败排除”；
- 健康窗口样本数达到门槛，但成功率低于最小成功率；
- 探测数据超过新鲜度窗口；
- 倍率数据缺失或超过新鲜度窗口。

生成建议前必须满足：

- 当前 `accounts.schedulable=true`；
- 当前账号没有 active gate state；
- 同平台仍有其他 active + schedulable 账号可承接；
- 候选仍处于监控映射启用状态。

### 6.2 恢复账号建议

被闸门暂停的账号满足以下条件时，生成“恢复账号承接”建议：

- 最新探测在新鲜度窗口内；
- 最新倍率在新鲜度窗口内；
- 不命中最近探测失败、连续失败、成功率低、倍率缺失 / 过期等排除原因；
- `upstream_relay_account_gate_states.active=true`；
- 当前 `accounts.schedulable=false`。

第一阶段只做“恢复建议”，不自动恢复。

原因是恢复动作会重新引入流量，比关闭更容易引发成本或稳定性问题。

### 6.3 兜底保护

暂停账号前必须检查：

- 不能暂停同平台最后一个 active + schedulable 账号；
- 只对当前仍可调度的账号生成暂停建议；
- 只恢复由本功能暂停且 gate state 仍 active 的账号；
- 应用时必须校验当前 `schedulable` 仍等于建议生成时的旧值；
- 应用 priority 时仍必须校验当前 priority 仍等于建议生成时的旧值；
- 如果数据不足，优先生成排除原因，不直接执行。

这几条比复杂评分更重要，因为它们防止自动策略把系统带进不可用状态。

## 7. 策略配置建议

第一版配置保持克制。

v1 不新增复杂配置，优先复用现有推荐策略和监控新鲜度窗口。

后续如需扩展，可以增加或复用以下配置：

- 是否启用自动闸门建议；
- 是否允许生成暂停账号建议；
- 是否允许生成恢复账号建议；
- 余额低水位阈值；
- 余额新鲜度窗口；
- 账号暂停冷却时间；
- 账号恢复连续成功次数；
- 单轮最大暂停账号数；
- 单轮最大恢复账号数；
- 是否禁止暂停同平台最后一个可调度账号。

不建议第一版暴露复杂权重：

- 成本权重；
- 延迟权重；
- 成功率权重；
- 余额权重；
- 自定义表达式。

这些配置看起来灵活，但会让运营难以判断策略为什么做出某个动作。

## 8. 推荐记录应该如何展示

推荐历史需要能回答三个问题：

1. 为什么建议关闭或开启？
2. 影响哪个项目账号和哪些上游入口？
3. 管理员现在该不该执行？

建议每条建议展示：

- 动作类型：调整 priority / 暂停账号 / 恢复账号；
- 项目账号、连接器、上游分组；
- 当前 priority；
- 当前调度状态和建议调度状态；
- 最新倍率和倍率来源；
- 最近探测状态；
- 健康摘要；
- 余额和余额检查时间；
- 今日成本和 token；
- 建议原因；
- 风险等级；
- 是否可自动应用；
- 如果不可自动应用，说明跳过原因。

文案应该使用业务语言，而不是只展示字段名。例如：

- “最近一次探测失败，且同平台仍有其他可调度账号，建议暂停该账号承接。”
- “余额检查已超过 24 小时，无法确认该上游账号是否仍可承接新流量，本轮只生成建议。”
- “账号此前由流量闸门暂停，当前倍率和探测已恢复新鲜，建议人工确认后恢复承接。”

## 9. 自动应用策略

第一版自动应用只允许继续处理 `priority_update`。

遇到 `account_pause` 或 `account_resume` 时，自动应用安全门必须跳过该 run，并返回明确原因：`account_gate_suggestion_requires_manual_apply`。

这样做是刻意保守：

- 暂停账号会直接影响真实请求调度；
- 恢复账号会重新引入流量，可能带来成本或稳定性波动；
- 管理员需要先看到原因、健康摘要、倍率来源和影响账号，再手动确认；
- 当前 v1 的 gate state 记录已经能保证手动恢复只恢复本功能暂停过的账号。

## 10. 与现有能力的关系

### 10.1 `accounts.schedulable`

账号流量闸门 v1 的真实写入目标是 `accounts.schedulable`。

暂停账号承接时：

- 校验当前 `schedulable` 仍等于建议里的 `old_schedulable`；
- 更新为 `false`；
- 写入或更新 `upstream_relay_account_gate_states`；
- 写 scheduler outbox。

恢复账号承接时：

- 要求存在 active gate state；
- 校验当前 `schedulable` 仍等于建议里的 `old_schedulable`；
- 更新为 `true`；
- 标记 gate state restored；
- 写 scheduler outbox。

### 10.2 候选 `enabled`

候选 `enabled` 仍然保留，但语义是监控候选映射开关。

它用于表达：

- 是否把这个连接器 + 上游分组 + 本地账号映射纳入监控；
- 是否参与推荐输入；
- 管理员是否临时隐藏某个候选映射。

它不作为 v1 的真实流量阻断字段。文档、UI 和接口说明都应避免把 `upstream_relay_candidates.enabled=false` 描述为“请求不会打到该账号”的保证。

### 10.3 账号级操作入口

第一阶段建议在推荐历史中提供账号级手动应用：

- 暂停该账号承接；
- 恢复该账号承接；
- 查看触发建议的上游分组、探测原因和倍率来源；
- 查看 gate state 是否来自本功能。

### 10.4 连接器 `paused`

连接器已有 `paused` 状态，但第一阶段不建议自动使用。

连接器级暂停适合这些场景：

- 登录态失效；
- 账号余额极低；
- 上游整体不可用；
- 管理员明确暂停某个上游入口。

它的影响面比候选级关闭大，应该先作为人工动作保留。

### 10.5 推荐系统

现有推荐系统可以继续生成 priority 建议。

新增闸门后，推荐系统应先判断候选是否应进入自动路由池：

1. 不适合承接流量且仍可调度的账号，生成暂停账号建议；
2. 已由闸门暂停且恢复条件满足的账号，生成恢复账号建议；
3. 其余健康候选，再参与 priority 排序。

## 11. 分阶段落地

### R1：策略文档和需求收敛

- 明确业务目标；
- 明确第一阶段落到 `accounts.schedulable`；
- 明确账号闸门建议只手动应用；
- 明确不做复杂规则引擎。

### R2：账号暂停建议

- 后端生成暂停账号建议；
- 推荐记录支持动作类型；
- 前端展示暂停原因、影响对象、风险等级；
- 不直接自动执行。

### R3：手动应用账号闸门

- 应用暂停建议时更新 `accounts.schedulable=false`；
- 应用恢复建议时更新 `accounts.schedulable=true`；
- 增加同平台最后可调度账号保护；
- 增加 gate state 记录暂停来源和原因；
- 支持从推荐历史手动应用。

### R4：恢复建议

- 对本功能暂停的账号生成恢复建议；
- 恢复建议默认人工确认；
- 展示探测恢复、倍率恢复、gate state 等依据。

### R5：有限自动恢复

只有在前几轮运行稳定后再考虑，且不属于 v1。

自动恢复必须满足更高门槛，并保留单轮恢复上限。

---

## 12. 验收标准

- 管理员能看到“暂停账号”和“恢复账号”建议，而不只是 priority 建议；
- 每条建议能解释触发原因和影响对象；
- 系统不会暂停同平台最后一个 active + schedulable 账号；
- 管理员能从推荐历史手动暂停或恢复账号承接；
- 自动应用开启时，账号暂停 / 恢复建议仍会被跳过并返回明确原因；
- 人工 `schedulable=false` 且没有 gate state 的账号不会被策略恢复；
- 本功能暂停的账号可以在恢复条件满足后进入恢复建议；
- 所有自动执行动作都有历史记录和可审计原因。

## 13. 后续实现前检查

进入实现前，需要补充确认：

- Trellis 任务 base branch 应改为 `custom/main`；
- `implement.jsonl` 和 `check.jsonl` 应包含下游 fork 工作流约束；
- 数据库迁移需要记录账号闸门暂停来源、原因、时间和恢复条件；
- 后端需要区分人工关闭和闸门暂停；
- 前端推荐历史需要支持多动作类型展示；
- 自动应用前需要跳过账号闸门建议并展示原因。
